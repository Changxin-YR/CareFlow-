## 缺口 A｜PRIM003 老年人健康管理技术规范（仍阻塞，最高价值）

| 项 | 内容 |
|---|---|
| **文档编号** | `PRIM003` |
| **标准号** | **WS/T 484—2015** |
| **标题** | 老年人健康管理技术规范 |
| **发布机构** | 国家卫生和计划生育委员会（现国家卫生健康委） |
| **权威等级** | **P0**（国家现行卫生标准，最高等级） |
| **发布/实施** | 发布 2015-11-04 ／ 实施 **2016-04-01**（已从发布页确认，是 manifest 中 `effective_date` 仅有的 2 篇之一） |
| **官方入口** | https://www.nhc.gov.cn/wjw/c100309/201511/6725aa6b7b6846058e3abf6ab3ee32d4.shtml |
| **当前状态** | **仍阻塞（FAILED）** —— 仅有发布页元数据 **281 字符**，正文实质缺失，贡献 **1 个切片** |

### 为什么缺

官方 PDF（`knowledge/raw/07_primarycare/PRIM003.pdf`，39 页，3.9 MB）**有文本层但编码损坏**：
`ToUnicode` CMap 是坏的，抽出的是 `犐犆犛１１．０２０`（本应是 `ICS 11.020`）。

### 最重要的提醒：不要再追这个链接

> **交接文档给出的「官方完整 PDF」直链下载下来，与我们已有的文件 `SHA256` 完全相同。**

```
https://www.nhc.gov.cn/ewebeditor/uploadfile/2016/01/20160128143208616.pdf
→ HTTP 200, application/pdf, 3,934,877 字节, 39 页
→ SHA256 = f8e5ca3ba30fa29632dcc6a8c75573cac1142000858b2d0da4502e9864e4bb40
→ 与 knowledge/raw/07_primarycare/PRIM003.pdf 的 SHA256 **完全一致**
```

**即：这是同一份坏文件。** 换它不会带来任何改善，纯属白跑一趟。

### 损坏程度（PyMuPDF 实测，全文 28,418 字符）

| 码位区间 | 数量 | 含义 |
|---|---:|---|
| `U+00xx` 控制区 | 19,250 | 中文被映射到这里 |
| `U+FFxx` 全角区 | 6,739 | 数字/标点被映射成全角 |
| `U+72xx` | 234 | 26 个英文字母被映射到 CJK 区 |
| 常用汉字（的一是不了…） | **0** | 一个都没有 |

**无法程序性还原的原因**：逐字符偏移**不恒定**（26 个字母对应 12 种不同偏移），
说明这是「字形索引 → Unicode」的**错误映射表**，不是简单位移，无法算术反推。

### 需要找什么（任一即可）

1. **同一份 PDF 的另一个版本**，带正确的文字层
   （很多标准在「卫生标准网」「国家标准全文公开系统」上有可复制的版本）；
2. **官方 Word / HTML 版全文**；
3. **扫描件也可以**，但要能 OCR 且愿意人工校对（见下方「OCR 路径」）。

### 去哪找

| 渠道 | 入口 | 说明 |
|---|---|---|
| 卫生标准网 | `wsb.nhc.gov.cn` | 卫健委标准发布平台，可查 WS/T 系列 |
| 国家标准全文公开系统 | `openstd.samr.gov.cn` | 部分卫生行业标准可在线看/下载 |
| 卫健委标准查询 | `www.nhc.gov.cn/wjw/` | 官方标准发布栏目 |
| 标准发布机构 | 国家卫生健康委标准专业委员会 | 可申请带正确 `ToUnicode` 的电子版 |

### 怎么判断「找对了」

1. 打开文件，能看到正常的 **`ICS 11.020`**、**`WS/T 484—2015`** 字样（不是 `犐犆犛`）；
2. 复制一段中文，粘贴出来是**正常汉字**（不是控制字符或方框）；
3. 页数/章节结构与 39 页 PDF 一致（可用于交叉验证内容完整性）；
4. **`SHA256` 不能与** `f8e5ca3ba30fa29632dcc6a8c75573cac1142000858b2d0da4502e9864e4bb40` **相同**
   —— 相同就说明又拿到了那份坏文件；
5. 入库后跑 `python scripts/verify_content_match.py`，该文档应显示 **`OK ratio>=0.34`**。

### OCR 路径（当前推荐）

该 PDF **是扫描/渲染可用的**（页面图像正常，只是文字层坏了），因此可以：

1. 用 OCR 工具渲染识别这 39 页；
2. **人工校对，尤其数字**（`140` 可能被认成 `14O`、`0` 与 `O`、`1` 与 `l`）；
3. 校对**完成后**才置为 `active` 进入生产检索。

> ⚠️ **校对前不得置为 active。** 乱码/错字 Citation 直接违反契约
> 「**真实 Citation > 漂亮回答**」——与其给用户一段 `犐犆犛１１．０２０` 的引用，
> 不如不给。这也是当前用发布页元数据占位的原因。

> **关键澄清：问题不是"没抓到"，而是官方发布的附件本身就是无文本层扫描件。**

| `LIFE001` | 5,473,222 | 388 字符 | 保留发布页正文（1325 字符） | **部分解决** |
| `LIFE001A` | 6,580,831 | 391 字符 | **置 draft**（`title_bigram_ratio=0.111`） | **部分解决** |
| `LIFE001B` | 5,580,591 | 405 字符 | **置 draft**（`title_bigram_ratio=0.111`） | **部分解决** |
| `LIFE001C` | 5,483,126 | 418 字符 | **置 draft**（`title_bigram_ratio=0.053`） | **部分解决** |
| `LIFE008` | 42,903（1 页） | 106 字符 | 保留发布页正文（594 字符） | **部分解决** |

**这些官方 PDF 都保留在 `knowledge/raw/` 下**，可直接用于 OCR，不必重新抓取
（也避免再次触发 WZWS 风控）。

### 怎么判断「找对了」

- **不要**再去找同一个附件 PDF —— 它没有文本层；
- 需要的是：① 带文本层的同文版本，**或** ② 该附件的 **OCR + 人工校对**结果；
- 判据同上：能复制出正常中文、`verify_content_match.py` 显示 `OK ratio>=0.34`。

### 重要：`LIFE001A/B/C` 为什么置 draft

这 4 份官方附件**全部是扫描件**（每份仅约 400 字符版式文字）。
`title_bigram_ratio` 0.053~0.111 说明**文件内容里几乎找不到标题字样**，证明抓到的不是正文。
把「内容与标题不匹配」的文件放进检索会**污染 Citation**，因此置为 `draft`
（生产检索只用 `active`），文件与 `SHA256` 保留作为来源记录。

**OCR 校对完成后**再把它们改回 `active`。

> 📋 **OCR 的具体操作步骤见 [`docs/OCR_WORKFLOW.md`](./OCR_WORKFLOW.md)**：
> 生成草稿 → 逐页对照 → 写出校对产物（含 `reviewed: yes` 标记）→ 入库。
> 注意其中列出的**两个必踩的坑**（`annex_pdf` 与 `secondary_files` 不清空会导致新文件不被使用），
> 以及 `build_manifest.py` 的 `FORCE_DRAFT` 名单需要同步移除。

## 找到文件后的标准入库流程

> 交给**懂一点命令行**的人做，或者直接交给研发。

### 第 1 步：放文件

把文件放到对应域目录，**文件名必须是 `<文档编号>.<扩展名>`**：

```
knowledge/raw/01_core/CORE002.pdf
knowledge/raw/06_lifestyle/LIFE001.pdf
knowledge/raw/07_primarycare/PRIM003.pdf
knowledge/raw/08_who/WHO001.pdf
```

扩展名只支持 **`.pdf`** 和 **`.html`** 两种。
如果是 OCR 文本或 Word，请先转成 `.html`（用 `<h1>/<h2>/<p>` 标出标题与段落）。

### 第 2 步：更新下载报告（**这一步最容易漏**）

`preprocess_documents.py` 读的是 **`knowledge/raw/_download_report.json`**，**不是 manifest**。
在该文件里找到对应 `document_id` 的那一条，改这几个字段：

```jsonc
{
  "document_id": "PRIM003",
  "local_file": "knowledge/raw/07_primarycare/PRIM003.pdf",  // 指向新文件
  "ext": "pdf",                    // "pdf" 或 "html"
  "content_kind": "pdf",
  "status": "downloaded",
  "bytes": 3934877,                // 实际字节数
  "sha256": "<64位小写十六进制>",   // 见下方命令
  "error": "",
  "annex_pdf": null,               // 必须清空，否则会优先用旧附件
  "secondary_files": []            // 同上，必须清空
}
```

> **两个必踩的坑**：`annex_pdf` 和 `secondary_files` 只要有一个非空，
> `preprocess_documents.py` 就会**优先使用那个旧文件**，你的新文件不会被用上。
> 处理 PRIM003 时踩过一次。

算 sha256：

```powershell
# Windows PowerShell
(Get-FileHash "knowledge\raw\07_primarycare\PRIM003.pdf" -Algorithm SHA256).Hash.ToLower()
```

### 第 3 步：更新 manifest

```bash
python scripts/build_manifest.py      # 从报告重新生成 manifest
```

然后手工核对生成的 `knowledge/manifest/knowledge_manifest.csv`：
`local_file`、`sha256`、`status`（补齐后要改成 `active`）、`notes`（写清来源与授权）。

### 第 4 步：重跑管线并验证

```bash
python scripts/extract_publish_dates.py    # 抽发布/实施日期
python scripts/preprocess_documents.py     # 清洗
python scripts/build_chunks.py             # 切片（必须 0 verbatim problems）
python scripts/validate_manifest.py        # 必须 VALIDATION PASSED
python scripts/verify_sources.py           # 必须 VERIFY PASSED
python scripts/verify_content_match.py     # 该文档应显示 OK ratio>=0.34
python -m pytest tests/ -q                 # 期望 521 passed
python scripts/evaluate.py --provider mock # 期望 6 套 100%、RAG >=96.88%
```

## 验收标准

一篇文档算「补齐成功」，必须**同时**满足：

| # | 标准 | 怎么验证 |
|---|---|---|
| 1 | 本地文件存在且 sha256 与 manifest 一致 | `python scripts/validate_manifest.py` → `VALIDATION PASSED` |
| 2 | `status=active` | 同上 |
| 3 | 清洗后字符数**明显大于**原来的发布页正文 | 看 `_preprocess_report.json` 的 `chars` |
| 4 | **不是乱码** | `verify_content_match.py` → 该文档 `OK ratio>=0.34`，不是 `MISMATCH` |
| 5 | 切片是**逐字连续片段** | `build_chunks.py` → `0 verbatim problems` |
| 6 | 端到端可用 | `python -m pytest tests/test_live_knowledge.py -q` → 全绿 |
| 7 | **OCR 内容已经人工校对** | 逐条核对数字与术语（`140` vs `14O`）；流程见 [`OCR_WORKFLOW.md`](./OCR_WORKFLOW.md) |
